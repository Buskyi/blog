数据搬运过程

  1. Decode（单token生成，prefill结束后，seq_len=1），Transformer Decoder逐层串行计算：第1层算完再算第2层；全部层跑完，才输出1个token，不是每一层输出token。
  2. 硬件真实行为：每一步只加载当前层权重到片上缓存（L2 cache / SM Shared Memory），其余层权重保存在HBM显存。
  3. 粗粒度bound估算简化：一轮完整decode，所有权重恰好被访问一次，所以单token解码总权重访存量约等于完整模型权重大小。
  4. 数据搬运链路：

    权重不会直接从HBM送到计算单元。

Tiling（矩阵分块）两层含义

  1. 硬性必要分块：矩阵太大放不下片上存储，必须切块，否则程序无法运行，不属于性能优化。
  2. 访存复用优化分块：调整tile大小、访存顺序，提升片上数据复用，减少HBM访问。
    • Prefill长序列：激活矩阵B维度大，tile权重读一次可多次复用，tiling收益巨大。
    • 单请求Decode：激活矩阵B只有一行，tile读取后仅使用一次，复用收益很小，因此decode为带宽瓶颈。

三个变量对单token decode延迟的影响（带宽受限场景）

  1. 算力翻倍：算力本身富余，几乎不降低延迟。
  2. 带宽翻倍：瓶颈是HBM权重读取，带宽翻倍，延迟近似减半。
  3. 批内权重复用（batch推理）：一轮kernel权重只读取一次，服务batch内全部token；B越大，单token分摊的访存字节越少，降低单token访存开销。

Prefill vs Decode

  • Prefill（处理输入prompt）：计算密集，算力瓶颈
  • Decode（逐一生成token）：访存密集，带宽瓶颈，逐层读权重 + 读写KV‑Cache

静态Batch vs Continuous Batching（vLLM核心）

1）静态Batch（教材例题默认模型，请求粒度打包）

同一batch内请求同进同出，同一个kernel完成一轮decode：

  1. 一轮内batch中A/B/C并行同时计算。
  2. 必须本轮全部请求执行完毕，才可以发起下一轮kernel。
  3. 尾巴问题 straggler：如果某个请求提前EOS结束生成，依然占用batch槽位，要等待同batch全部请求本轮跑完，才能重组batch，造成算力、带宽浪费。

2）Continuous Batching 连续批处理（token粒度打包）

核心：不按请求绑定batch，每一轮kernel都从活跃请求池重新挑选一批待生成token组成batch。

  • 请求完成EOS直接移出调度池，不需要等待同batch其他请求。
  • 请求生命周期互相解耦，消除静态batch的尾巴浪费。

示例时序：

  • Step1 batch={A,B,C}，执行后B到达EOS退出
  • Step2 重新选活跃请求，batch={A,D,E}，不再包含B

基础符号与核心公式

  • ：一批并行decode的请求数量（batch size）
  • ：模型总参数量
  • ：每个参数字节数
  • ：GPU稠密矩阵峰值算力
  • ：HBM显存带宽

  • 单token分摊权重访存字节： ；越大分摊越少。

说明：与B无关：一轮kernel权重只读一遍，给batch中所有token复用；
与B成正比：每个token独立做矩阵‑向量乘，B翻倍总计算量翻倍。

理想时间下界（仅考虑权重，忽略KV）

：一轮decode step总耗时，生成B个新token

  • ：纯计算理论最小耗时
  • ：纯权重读取理论最小耗时
  • ：访存、计算流水线重叠，总耗时由更慢那一方决定。

临界batch （计算耗时 = 访存耗时）

  • ：访存瓶颈；增大B可以分摊权重读取，吞吐快速上涨
  • ：算力瓶颈；吞吐增长变平缓

现实约束：是纯理论值，受显存容量限制，往往达不到。
例：H100，权重占73.73GB，剩余可用显存6.27GB；单条8192上下文KV占2.68GB。

最多同时存放2条请求的KV，远小于理论。

吞吐上界


单位：token/s，每批输出token数量除以理论最小step耗时。

⚠️理想下界成立条件非常苛刻：块大小完美、缓存充足、无同步、无KV抢占带宽、无kernel启动开销、带宽算力100%打满。真实环境一定存在损耗。

加入KV‑Cache读写的完整时间下界（书中实测模型）

：单条请求单步计算量；：单条请求单步KV读写字节

  • 固定； 随B线性增大；B上升，KV总访存变大，访存耗时增加，TPOT上升。

实测指标：TPOT 与 TTFT

TPOT（Time Per Output Token，每输出token时间）

用户侧：相邻输出token之间的平均间隔，表征流式生成节奏。

书中测量流程：

  1. 每个请求取首末输出时间差，除以输出间隔数；
  2. 同batch所有请求取中位数；
  3. 同一配置跑3次实验，再次取中位数消除抖动。

TTFT（Time To First Token，首token延迟）

用户提交完整prompt → 收到第一个输出token的时间，对应prefill阶段耗时。

实测曲线特点

吞吐曲线：斜率越来越小（上凸）
理想无KV开销：不变，吞吐正比于，直线。
真实：B增大，KV读写增加，（TPOT）变长，抵消部分吞吐增益，增长放缓。

TPOT曲线：斜率越来越大（下凹，延迟加速上涨)
理想恒定带宽：访存耗时对B是直线，每增加1条请求延迟增加。
真实两点原因：

  1. 权重读取与 KV读写共享HBM总线；B变大流量增大，总线冲突排队，实际有效带宽下降。
  2. 高并发下PagedAttention页查找、内存事务、GPU调度等额外非线形开销增大。

利用率指标

MBU（Memory Bandwidth Utilization，显存带宽利用率）


衡量HBM显存总线有效传输占比，最大值1。

上下文变长 → 上升 → 同等B总访存字节上升 → MBU上升。

CFU（Compute Flop Utilization，算力利用率）


衡量GPU计算单元有效利用，最大值1。

上下文变长 → 上升 → 同等B总FLOPs上升 → CFU上升。

规律：哪一侧是瓶颈，哪一侧利用率会随负载趋近1；另一侧利用率不会明显上升。

Kernel、eager模式、PCIe、驱动、日志

Kernel

GPU kernel：跑在GPU上的可执行小程序；矩阵乘法、layernorm、softmax、KV写回都各对应kernel。

  • eager模式：逐个提交kernel；CPU做完准备，提交一个kernel，等GPU完成再提交下一个。
  • 算子融合fusion：多个小算子合并成一个kernel，CPU只提交一次，减少提交开销。

eager模式完整执行时序

  1. 模型加载阶段，kernel二进制已经上传保存在GPU侧。
  2. CPU(Python)准备张量地址、形状等参数，调用CUDA API。
  3. GPU驱动打包任务描述指令，通过PCIe总线发给GPU。

    PCIe：CPU主机与GPU之间的硬件通信通道；只传递控制指令、完成信号，不搬运权重/特征张量，张量保存在GPU的HBM显存。

  4. GPU执行本地kernel，读写HBM显存完成计算。
  5. GPU计算完毕，通过PCIe向CPU发送简短“任务完成”信号。
  6. CPU收到信号，继续执行Python，准备下一个kernel，重复上述流程。

主机=CPU侧（Python、vLLM服务、驱动）；加速器=GPU。
eager模式问题：两个kernel中间，CPU处理任务，GPU空转等待指令；硬件本身能力没问题，是软件调度带来的开销。

逐步记录日志的开销

日志代码运行在CPU主机上，不在GPU执行：获取时间戳、格式化、打印/写日志文件。

危害：与准备kernel任务争抢CPU时间。GPU完成信号返回后，CPU优先执行日志逻辑，延迟下一个kernel指令下发，进一步拉长GPU空转时间，增大TPOT。关闭日志可以消除这部分开销。

实测达不到理论极限的两类根源

第一性原理：用硬件标称规格直接算出理论物理上的时间下界，再对比实测，区分差距来源。

  1. ①理论模型漏项（硬件必须执行，不能消除）
    估算只计入权重、KV读写；忽略向量运算、采样等必须运算。
    👉 处理：把遗漏工作量补入估算公式，抬高理论下界，缩小和实测差距。

  2. ②实现本身的系统开销（软件层面，可以消除）
    eager逐kernel提交开销（Python、驱动、PCIe交互，GPU空转）；逐步记录日志占用CPU。
    👉 处理：算子融合，减少kernel提交，关闭冗余日志。

书中实验数据：

  • 理论访存下界：8.62 ms
  • eager+开启日志完整实测TPOT：26.5 ms，MBU仅33%
  • 关闭日志：12.1 ms
  • 仅统计GPU内部执行时间：10.7 ms，和理论下界只差约20%

三倍差距主要来自主机侧软件开销，不是GPU硬件本身。

FPGA

Field‑Programmable Gate Array，现场可编程门阵列

CPU/GPU：出厂硬件电路固定。CPU 跑软件指令；GPU 跑编译好的 kernel。
FPGA：硬件电路可以 “现场改写重配置” 的芯片。不用流片制造新芯片，就可以修改芯片内部逻辑电路。
