ai infra

操作系统的职责：

  1. 设备权限管理：AI 进程想访问 GPU/NPU，必须通过 OS 申请，OS 把加速器设备分配给这个进程，防止多个程序乱抢硬件。
  2. 底层设备驱动加载：OS 加载硬件驱动，驱动提供最基础的接口，让用户态程序可以和加速器硬件通信。
  3. 内存基础保护：防止程序越界访问别的进程的显存，做安全隔离。

👉 这部分绝对绕不开。没有 OS，你的程序根本打不开、用不了这块加速器。

一旦 OS 把加速器分配给你的 AI 进程，卡里面的所有细节调度，就交给 AI Infra（编译器 + Runtime）：

  • 怎么切分 HBM 显存，哪块存权重、哪块存激活、KV Cache；
  • 识别算子依赖，做算子融合；
  • 规划片上缓存，决定中间结果要不要写 HBM；
  • 生成硬件指令，控制 DMA 搬运数据、启动计算单元。

加速器硬件的访问权限，需要操作系统给；但加速器卡内部：显存怎么划分、片上缓存怎么用、算子怎么跑、数据什么时候搬运，由 AI Infra 自己管，不再交给 OS 来做。

CPU Runtime

AI Runtime（运行时）是 AI Infra 的一部分，跑在 CPU 上！ AI Infra 不是只在 GPU，它分成两部分：

  • CPU 侧 Runtime：管理请求队列、内存、张量、准备任务、组装指令、调用驱动，负责 “调度和准备工作”
  • GPU 侧：执行真正的算子计算、DMA 数据搬运

CPU Runtime 做的事情：

  1. 读取队列里已经编好 batch 的请求；
  2. 分配显存空间：给输入张量、KV Cache、中间结果预留显存；
  3. 生成要在 GPU 上执行的算子指令；
  4. 通过驱动，提交任务给 GPU；
  5. GPU 计算完成后，Runtime 拿回结果，拆包，把结果返回给各个用户。

为什么是 CPU 运行时向 GPU 提交任务？前面不是说 AI Infra 管理吗？

关键点：AI Infra 是整套系统，CPU Runtime 是 AI Infra 的 CPU 组件，GPU 算子库是 AI Infra 的 GPU 组件。 不是 “CPU 是独立外部程序去指挥 GPU”，而是AI Infra 的 CPU 部分，指挥 AI Infra 的 GPU 部分。

batch

✅ batch 就是批处理。编入 batch = 把多条独立请求的 token 序列打包，合并成一个统一的张量，一起送入 GPU 计算。 不是一次性执行，是攒请求、组织打包这个动作叫编入。

举例子： 请求 1：你好 → token 序列 [101,234] 请求 2：介绍一下算子融合 → token 序列 [101,56,78,99] 两条请求先后到达，调度器把它们编入同一个 batch，拼成一个二维张量送入 GPU。

GPU 加速器擅长并行一次性算一整批，而不是一条一条串行算。

⚠️ 注意： 编入 batch 有代价：要短暂排队等待新请求进来。需要权衡延迟和硬件利用率（前面讲过）。

✅ 好处：一次 GPU 计算，同时处理多条请求，提升 GPU 利用率，提高整体吞吐 ❌ 代价：先到的请求 A，必须多等一会儿，才能等到 B、C 来凑 batch，这条请求的延迟变大了。

这就是书上说的权衡（trade-off）

  • 等久一点：batch 更大，GPU 利用率高，总吞吐高；但是单条请求的延迟会增加
  • 不等，来了就跑：延迟很低，但是 GPU 经常只跑 1 条请求，硬件利用率差，浪费昂贵 GPU 资源

补充：padding（补齐，很重要的细节）

三条请求 token 长度不一样：A 是 3 个 token，B 是 2 个，C 是 4 个。 拼成 batch 张量的时候，必须全部对齐到最长长度（4），短句子后面填充特殊占位 token。

这也是 batch 带来的额外小开销：填充的 token 也要参与计算，产生少量多余访存 / 计算。

文本转换

就是Tokenizer 分词：用户输入自然语言字符串 → 切割成 token 序列，再转成数字 ID（模型只认数字，不认文字）。 书上说可以两个地方做：

  1. 共享前端（路由器 / 网关那一层）：在请求进入推理实例之前，就把文字转成 token ID；好处：各个实例不用重复做分词，减轻实例压力。
  2. 推理实例内部：原始文本直接发给实例，实例内部自己做分词。

文本转换属于预处理，还没进入神经网络算子计算阶段。

各有优劣

token

token（词元）是模型处理文本的最小碎片，可以是单字、词语，也可以是单词的一部分片段；分词算法由模型自带的 tokenizer 决定，同一文本在不同模型下 token 数量不同。

中文粗略估算：1000 汉字≈1000~1300 token；英文 1000token≈750 单词。

每个 token 推理时会生成 KV Cache，占用显存；token 长度直接影响推理实例能承载的并发请求数量。

token ID

分词器把文字切成一个个 token 片段之后，给每一个 token 分配一个唯一的整数编号，这个一串整数，就是 token ID 数字列表。

prefill和decode

Prefill（预填充） Decode（解码）
输入 用户全部输入 token，一次性并行输入 仅上一步刚生成的1 个新 token
计算特点 大量 token 并行，矩阵乘法为主，算力密集 每次只处理 1 个 token；大量读取 KV Cache，访存密集
KV Cache 生成所有输入 token 的 K、V，存入显存 读取历史 KV；新增当前 token 的 K、V 追加进缓存
速度特点 长文本 prefill 会比较慢，但一次算完 每次生成一个字，速度受 HBM 读取带宽限制

什么是 K（键）、V（值）向量？

这是 Transformer 注意力机制里面的数据，是浮点数向量，不是文字，不是 token ID。

简单类比注意力机制： 你在写作文，看着前面的上下文，判断哪些词是重点。

  • Q Query 查询向量：当前正在处理的这个 token 的 “问题”：我需要关注哪些历史信息？
  • K Key 键向量：历史每个 token 的 “索引标签”
  • V Value 值向量：历史每个 token 对应的实际内容信息

注意力的逻辑： 拿当前 Q，去和所有历史 K 做匹配，看哪些历史 token 和当前 token 相关； 根据匹配权重，把对应的 V 融合起来，得到这一步的结果。

K、V 就是每一个 token 经过网络变换之后得到的向量。 Prefill 阶段算出来之后，存进 KV Cache；后续解码阶段直接读取，不再重复计算 K、V。

KV Cache

KV Cache 本身一直放在 HBM（显存）里；每次注意力计算时，DMA 会把需要的 K、V 向量小块，从 HBM 搬运到片上 SRAM 缓存，给 MAC / 注意力单元读取。

和模型权重的访问模式很像：KV 本体常驻 HBM，计算时 DMA 分块搬到片上缓存，不会一次性把全部 KV 都放到片上缓存（片上 SRAM 太小放不下长序列的全部 KV）。

硬件概念

DMA 本质是硬件搬运通道，可以在不同存储之间搬数据，但不是 “随便到处直接访问”，要看硬件链路。 DMA 可以做这些搬运：

  1. 硬盘 ↔ CPU 内存（主机内存）
  2. CPU 内存 ↔ HBM（加速器显存）
  3. HBM 内部：HBM ↔ 片上 SRAM（这也是 DMA）

DMA = Direct Memory Access，直接内存访问。

HBM = High Bandwidth Memory，高带宽内存，专门用在 GPU/NPU 大加速器卡上的显存。

片上缓存 SRAM 类比 cpu 的 cache？

问：CPU 访问内存时，硬件自动把数据加载进 cache；GPU 访问 HBM 的时候，硬件会自动把数据预取到片上 SRAM 吗？

答：不会（大部分 AI GPU/NPU），需要算子 / 编译器通过 DMA 显式搬运，手动分块 tiling。

权重加载一次，生成时逐步读取。

超节点

一个超节点由1或多张加速器（显卡）组成

把一个超节点的硬件资源，分配给一个推理实例。

实例使用这个超节点内所有加速器，处理请求。

超节点 = 硬件资源组；推理实例 = 跑在硬件上的软件服务单元。

✅ 单条请求可以在同一个超节点内部跨多卡并行计算（高速 NVLink，适合张量并行）

❌ 单条请求不能跨两个不同超节点拆分计算（跨超节点网络太慢，代价巨大）

在服务器或计算托盘内，CPU 连接主存，负责主机程序和执行控制；GPU 连接各自的显存，执行模型计算、保存运行所需的数据。HBM（高带宽内存）是加速器常用的一类显存，通过宽接口持续提供数据。CPU 与 GPU 可以通过 PCIe（高速外设互联）连接，GPU 之间也可以通过独立的高速互联直接交换数据。

decoder-only vs CED

  • 传统 decoder-only 模型，输入 prompt 与生成输出 token 共用同一套解码器主干，执行路径对称。Agent 场景输入 token 多、输出 token 少时，每一步解码都要读取全部输入 token 的 KV，开销高。

  • CED 架构执行路径不对称：长输入由编码器一次性计算并压缩得到全局 KV；解码器仅基于全局 KV 生成输出，原始输入 token 不再进入解码器。通过拆分两条不同的计算路径，重新分配算力，降低长输入、短输出场景下解码阶段的开销。

量化

量化：把原来精度很高的浮点数权重，用更少比特的整数来存；保存一个缩放系数 scale，推理的时候用 scale 把整数还原回近似的浮点数。 目的：减少每个权重占用的字节，降低 HBM 显存占用、减少 DMA 搬运的数据量，代价是一点点精度损失。

拿文中例子：BF16（16 位浮点）→ INT8（8 位整数）

  • BF16：每个权重占 2 字节（16bit），可以表示很大范围的小数，精度高。
  • INT8：8 位整数，只能存 -128 ~ +127 的整数，没法直接存浮点数。

量化两步（离线，模型保存时做）

  1. 找到这一层所有权重的最大值、最小值
  2. 算出缩放因子

把原始浮点数权重，除以 scale，四舍五入，压缩到[-128,127]这个整数区间，存成 8 位整数。

原始浮点数 → 除以 scale → 变成 INT8 整数保存。现在每个权重只占 1 字节。

反量化两步（推理时，GPU 读进显存之后，计算之前）

读取 INT8 整数，乘以 scale，还原成近似浮点数，用来做矩阵乘法。

保存：浮点数 → 压缩成 INT8 推理：INT8 × scale → 近似浮点数

重点：权重是全局一份；KV Cache 是每条请求单独一份。多条并发请求，KV 缓存会叠加，显存开销会暴涨。

  1. ：工作区 GPU 做矩阵运算、中间临时计算结果、算子缓冲区，需要预留一块显存空间，叫工作区。本例预留 2.15GB（2GiB）。
